# API v1 contract

This document defines the minimum stable contract required before implementing
the public HeartPhrame API. It does not expose existing web controllers as an
API. Web routes remain dedicated to the HTML interface, while the API receives
separate versioned routes, authentication, DTOs, and compatibility rules.

## 1. Goal and boundaries

- The API root is `/api/v1`.
- The first version supports JSON and UTF-8.
- Every domain module remains the owner of its data, validation, and ACL
  decisions.
- `module-api` provides the shared HTTP layer but never reads another module's
  tables directly.
- Existing web routes and session login are not part of the public API contract.
- Removing `module-api` disables the API without breaking the other modules.
- An API key can never grant a user a permission they do not have in the
  application.

## 2. Module ownership

| Module | API responsibility |
|---|---|
| `module-api` | Route versions, JSON responses, problem responses, pagination, OpenAPI, CORS, rate limiting, request IDs, and the idempotency registry |
| `module-auth` | API keys, key authentication, scopes, user identity, local user/group CRUD, and auth audit |
| `module-workspace` | Workspaces, trees, nodes, workflow, and Workspace ACL |
| `module-editor-html` | Documents, languages, versions, HTML, attachments, and the published view |
| `module-calendar` | Calendars, events, recurrence, calendar ACL, and ICS |
| `module-task` | Task definitions, current state, and change history |
| `module-notification` | Current-user notifications |
| `module-email` | No public arbitrary-email endpoint; remains an internal service |
| `module-theme` | Optional read-only description of the active public theme |
| `module-menu` | Optional read-only menu filtered for the current API identity |

A domain module registers its API routes only when `module-api` is installed.
The optional integration must not become a required Composer dependency.

## 3. API identity and keys

A key belongs to an existing active user. Authorization is evaluated in this
order:

1. the key exists, is not revoked, and has not expired
2. the owning user exists and is active
3. the key contains the required scope
4. the user has the required domain permission through the existing ACL

The proposed key format is:

```text
hfp_live_<public-id>_<secret>
```

`public-id` locates the record. The secret is generated by a cryptographically
secure generator, displayed once, and only its hash is stored. It must never be
written to audit records, exceptions, access logs, or HTML.

Each key contains:

- a name and optional description
- `user_id`
- a set of scopes
- an expiration timestamp or `null`
- `created_at`, `last_used_at`, and `revoked_at`
- an optional IP allowlist
- a public prefix for safe identification in administration

## 4. Scopes

The initial registry uses stable ASCII names:

```text
workspace:read
workspace:manage
page:read
page:write
page:publish
attachment:read
attachment:write
calendar:read
calendar:write
task:read
task:write
users:read
users:create
users:update
users:delete
groups:read
groups:manage
notifications:read
notifications:write
webhooks:read
webhooks:manage
```

`page:write` covers creating a page and its first draft, editing or discarding
a draft, translation, version restoration, and deletion. `page:publish` is the
separate review and publication permission. `groups:manage` covers group
creation, updates, deletion, and adding or removing members.

Administrator status alone is not sufficient for an API operation. A key owned
by an active administrator must also contain the required scope. `users:*` and
`groups:*` endpoints operate only on local Auth records; they do not manage
users in SAML, CAS, OIDC, or OAuth providers.

`DELETE /users/{id}` deactivates the local account and revokes its API keys.
Physical deletion is not an API operation because it would break audit,
ownership, and historical references.

## 5. Shared HTTP contract

### Request

- `Authorization: Bearer <api-key>`
- `Accept: application/json`
- `Content-Type: application/json` for a JSON body
- `Accept-Language` determines the default response language
- an explicit `lang` parameter takes precedence for multilingual content
- the client may provide `X-Request-Id`, and the server always returns it

### Successful response

```json
{
  "data": {},
  "meta": {
    "request_id": "opaque-request-id"
  },
  "links": {}
}
```

Collections use cursor pagination:

```text
page[limit]=50
page[after]=opaque-cursor
filter[...]=...
sort=field,-other_field
```

The default limit is `50`, the maximum is `100`, and cursors are opaque values
that clients must not parse.

### Error

Errors use `application/problem+json` and a stable machine-readable `code`:

```json
{
  "type": "https://heartphrame.example/problems/forbidden",
  "title": "Forbidden",
  "status": 403,
  "detail": "The current identity cannot read this resource.",
  "code": "resource_forbidden",
  "request_id": "opaque-request-id"
}
```

Production responses never contain SQL, stack traces, filesystem paths, or
secrets.

### Time and identifiers

- JSON timestamps use ISO 8601 in UTC, for example `2026-07-28T12:00:00Z`.
- Identifiers are JSON strings and remain opaque even when the internal key is
  numeric.
- A display name or slug never replaces a stable identifier.

## 6. Concurrent changes

Mutable resources return an `ETag`, and changes require a matching `If-Match`.
Editor additionally retains explicit `draft_revision` domain protection. A
stale ETag returns `412 Precondition Failed`, while a draft revision conflict
returns `409 Conflict`.

POST operations that clients may retry support `Idempotency-Key`. The same
user, endpoint, and request key must return the previous result without
repeating the business operation.

## 7. Initial resources

### Read-only v1 core

```text
GET /api/v1/me
GET /api/v1/workspaces
GET /api/v1/workspaces/{workspaceId}
GET /api/v1/workspaces/{workspaceId}/tree
GET /api/v1/pages/{pageId}
GET /api/v1/pages/{pageId}/attachments
GET /api/v1/calendars
GET /api/v1/calendars/{calendarId}
GET /api/v1/calendars/{calendarId}/events
GET /api/v1/tasks
GET /api/v1/tasks/{taskId}
GET /api/v1/notifications
```

Collections include only resources visible to the key owner. An inaccessible
single resource returns `404` when `403` would reveal the existence of a
private resource.

### Local user administration

```text
GET    /api/v1/users
POST   /api/v1/users
GET    /api/v1/users/{userId}
PATCH  /api/v1/users/{userId}
DELETE /api/v1/users/{userId}
GET    /api/v1/groups
POST   /api/v1/groups
PATCH  /api/v1/groups/{groupId}
DELETE /api/v1/groups/{groupId}
PUT    /api/v1/users/{userId}/groups
```

These endpoints require an active local administrator and the corresponding
`users:*` or `groups:*` scopes. The API never returns `password_hash`, provider
secrets, reset tokens, or sensitive configuration. A password is accepted only
when creating a user or explicitly changing it and is never returned.

## 8. Write operations

Drafts, publishing, attachments, events, and tasks use domain routes:

```text
POST  /api/v1/workspaces/{workspaceId}/pages
PATCH /api/v1/pages/{pageId}/draft
POST  /api/v1/pages/{pageId}/review
POST  /api/v1/pages/{pageId}/publish
POST  /api/v1/pages/{pageId}/attachments
POST  /api/v1/calendars/{calendarId}/events
PATCH /api/v1/calendar-events/{eventId}
PATCH /api/v1/tasks/{taskId}/state
```

### Webhook subscriptions

```text
GET    /api/v1/webhooks
POST   /api/v1/webhooks
GET    /api/v1/webhooks/{uuid}
PATCH  /api/v1/webhooks/{uuid}
DELETE /api/v1/webhooks/{uuid}
POST   /api/v1/webhooks/{uuid}/rotate-secret
GET    /api/v1/webhooks/{uuid}/deliveries
GET    /api/v1/webhooks/{uuid}/deliveries/{deliveryUuid}
POST   /api/v1/webhooks/{uuid}/deliveries/{deliveryUuid}/retry
```

A mutation completes before network delivery. The API stores a sanitized event
in the outbox, and a CLI worker signs it with HMAC-SHA256 and sends it with
bounded retry. The secret is encrypted at rest and returned only at creation or
rotation.

## 9. Compatibility

- New response fields may be added within `v1`.
- Existing fields do not change type or meaning within `v1`.
- Removing or redefining a field requires `/api/v2`.
- A new optional endpoint does not require a new major API version.
- OpenAPI is generated from the same registry that registers runtime routes.
- An internal PHP service signature does not automatically become part of the
  public HTTP contract.

## 10. Security minimum

Before the first public write endpoint is enabled, the implementation must
provide:

- hashed keys with one-time secret display
- key revocation and expiration
- scope and domain ACL checks
- rate limiting per key and IP address
- audit of write operations and failed authentication
- request-size limits
- safe MIME validation for uploads
- CORS disabled by default
- protection of sensitive data in logs and problem responses
